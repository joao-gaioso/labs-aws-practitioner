🏗️ Terraform 101

Tudo que você precisa saber antes de começar os labs. Se já conhece, use como revisão rápida.

💡 O que é Terraform?

Infrastructure as Code (IaC): você descreve o que quer ter na AWS em arquivos .tf e o Terraform cria, atualiza e destrói os recursos automaticamente. Em vez de clicar no console ou rodar comandos CLI, você escreve código versionável, reutilizável e auditável.

Estrutura de arquivos de cada lab

lab-XX-nome/ ├── main.tf # recursos AWS (aws_instance, aws_s3_bucket, etc.) ├── variables.tf # inputs configuráveis (região, tipo de instância, etc.) ├── outputs.tf # valores exportados após o apply (IP, URL, ARN, etc.) ├── provider.tf # configuração do provider AWS + default_tags ├── versions.tf # versão mínima do Terraform e do provider AWS ├── backend.tf # onde guardar o tfstate (local ou S3) └── src/ # código da Lambda (quando necessário) └── handler.py

Fluxo de trabalho

  • 1

    terraform init

    Baixa o provider AWS e inicializa o backend. Rode sempre que criar um novo diretório ou adicionar um novo provider.

  • 2

    terraform plan

    Mostra o que vai ser criado, modificado ou destruído — sem mexer em nada. Leia sempre antes do apply. O output mostra + criar, ~ modificar, - destruir.

  • 3

    terraform apply

    Executa as mudanças. Pede confirmação (yes) antes de aplicar. Use -auto-approve só em automação, nunca na mão.

  • 4

    terraform output

    Mostra os valores declarados no outputs.tf. Use terraform output -raw nome_do_output para pegar o valor sem formatação (útil em scripts).

  • 5

    terraform destroy

    Apaga todos os recursos gerenciados pelo state. Sempre rode ao terminar o lab para evitar cobranças.

Templates de partida — copie e adapte

provider.tf

provider "aws" {
  region = var.aws_region

  default_tags {
    tags = {
      ManagedBy = "terraform"
      Lab       = "lab-XX-nome"
    }
  }
}

versions.tf

terraform {
  required_version = ">= 1.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

variables.tf (padrão)

variable "aws_region" {
  description = "Região AWS"
  type        = string
  default     = "us-east-1"
}

variable "nome_projeto" {
  description = "Nome do projeto"
  type        = string
  default     = "lab-XX"
}

backend.tf (local)

terraform {
  backend "local" {
    path = "terraform.tfstate"
  }
}

# Para usar S3 como backend:
# backend "s3" {
#   bucket = "meu-bucket-tfstate"
#   key    = "lab-XX/terraform.tfstate"
# }
⚠️ Nunca commite o tfstate

O arquivo terraform.tfstate pode conter senhas, ARNs e chaves de acesso em texto claro. Adicione ao .gitignore: *.tfstate, *.tfstate.backup, .terraform/, *.pem.

Lab 01 · EC2 · ~35 min

Servidor Web EC2 com Terraform

"A ShopCloud precisa de um servidor web para hospedar a loja"

🎯 Contexto

Antes de trabalhar com serverless, entenda o que você está substituindo. Você vai criar uma EC2 com Terraform, configurar o Security Group para liberar HTTP e usar user_data para instalar o nginx automaticamente na primeira inicialização — tudo descrito como código.

📁 Estrutura esperada

lab-01-ec2-nginx/ ├── main.tf # data aws_ami, aws_security_group, aws_instance ├── variables.tf # aws_region, instance_type, nome_projeto ├── outputs.tf # ip_publico, instance_id, comando_ssh ├── provider.tf ├── versions.tf └── backend.tf

📋 Requisitos

  • R1 data "aws_ami" buscando Amazon Linux 2023 com filtro — sem hardcodar o ID
  • R2 aws_security_group com ingress na porta 80 (HTTP) e egress liberado
  • R3 aws_instance t2.micro com o Security Group associado
  • R4 user_data que instala nginx e cria /var/www/html/index.html com "ShopCloud"
  • R5 Output ip_publico expondo o IP da instância

💡 Dicas

Como usar data source para AMI?
Use data "aws_ami" com most_recent = true, owners = ["amazon"] e filtros por name = "al2023-ami-*-x86_64". Referencie com data.aws_ami.nome.id.
Como passar user_data no Terraform?
Use heredoc diretamente no resource: user_data = <<-EOF ... EOF. O Terraform automaticamente faz o base64 para a AWS. Comece sempre com #!/bin/bash.
Instância sem IP público?
Verifique se associate_public_ip_address = true está configurado no resource, ou se a subnet padrão da VPC já atribui IP público por padrão.
nginx não está respondendo?
O user_data roda só na primeira inicialização. Verifique os logs em /var/log/cloud-init-output.log. Confirme que a porta 80 está no Security Group, não 8080 ou 443.
✅
Critério de Sucesso
# Aplicar
terraform init && terraform apply

# Verificar — deve retornar 200
curl -o /dev/null -s -w "%{http_code}" http://$(terraform output -raw ip_publico)

# Cleanup ao terminar
terraform destroy

Lab 02 · S3 · ~25 min

S3 Static Website com Terraform

"A ShopCloud quer hospedar o site sem gerenciar servidores"

🎯 Contexto

A mesma página do lab anterior, sem servidor. O S3 serve HTML diretamente pelo navegador. Você vai criar e configurar o bucket inteiramente via Terraform — incluindo bucket policy, public access block e upload do arquivo HTML.

📁 Estrutura esperada

lab-02-s3-website/ ├── main.tf # aws_s3_bucket, website_config, public_access_block, policy, aws_s3_object ├── variables.tf ├── outputs.tf # website_url, bucket_name ├── provider.tf # adicionar provider "random" para nome único ├── versions.tf ├── backend.tf └── index.html # página da ShopCloud que você vai criar

📋 Requisitos

  • R1 aws_s3_bucket com nome único gerado por random_id
  • R2 aws_s3_bucket_public_access_block com todos os blocos desabilitados
  • R3 aws_s3_bucket_website_configuration com index_document = "index.html"
  • R4 aws_s3_bucket_policy com s3:GetObject para Principal = "*"
  • R5 aws_s3_object fazendo upload do index.html com content_type = "text/html"

💡 Dicas

Ordem importa: public_access_block antes da policy
Se o block_public_policy = true ainda estiver ativo, o Terraform vai falhar ao tentar aplicar a bucket policy. Use depends_on ou garanta que o public_access_block seja aplicado primeiro.
Como montar o website_url no output?
A URL segue o padrão http://BUCKET.s3-website-REGION.amazonaws.com. Use interpolação: "http://${aws_s3_bucket.nome.bucket}.s3-website-${var.aws_region}.amazonaws.com"
jsonencode para a bucket policy
Use jsonencode() do Terraform em vez de heredoc para a policy. Fica mais legível e evita erros de escape de aspas. O ARN do bucket é aws_s3_bucket.nome.arn.
aws_s3_object não atualiza o arquivo?
Adicione etag = filemd5("index.html") ao resource. O Terraform vai detectar mudanças no conteúdo do arquivo e fazer re-upload automaticamente.
✅
Critério de Sucesso
# Verificar — deve retornar 200 e o HTML da ShopCloud
curl -s $(terraform output -raw website_url)

# Abrir no navegador
echo $(terraform output -raw website_url)

Lab 03 · Lambda · ~45 min

Lambda + Function URL — API de Pedidos

"A ShopCloud precisa de uma API para consultar pedidos do DynamoDB"

🎯 Contexto

O padrão deste lab é o mesmo do lab-07-lambda-python que você já estudou. IAM Role, empacotamento com archive_file, CloudWatch Log Group e Function URL. A diferença é que o código Python aqui vai consultar o DynamoDB e retornar os pedidos em JSON.

📁 Estrutura esperada

lab-03-lambda-api/ ├── main.tf # iam_role, archive_file, lambda_function, log_group, function_url ├── variables.tf # aws_region, nome_projeto, runtime, timeout, table_name ├── outputs.tf # function_url, function_name, role_arn ├── provider.tf ├── versions.tf ├── backend.tf └── src/ └── api_pedidos.py # seu código Python aqui

📋 Requisitos

  • R1 aws_iam_role com trust policy para lambda.amazonaws.com + attachment de AWSLambdaBasicExecutionRole
  • R2 Policy inline com dynamodb:Scan e dynamodb:GetItem no ARN exato da tabela lab-pedidos
  • R3 data "archive_file" empacotando src/api_pedidos.py + source_code_hash no resource
  • R4 aws_cloudwatch_log_group com retention_in_days = 7 e depends_on na Lambda
  • R5 aws_lambda_function_url com authorization_type = "NONE" e CORS configurado

💡 Dicas

Decimal não serializa em JSON?
O DynamoDB retorna Decimal em campos numéricos. O json.dumps() nativo não sabe converter. Crie um DecimalEncoder customizado ou use float(v) antes de serializar.
source_code_hash por que é importante?
Sem ele, o Terraform não detecta mudanças no .py e não faz re-deploy. Com source_code_hash = data.archive_file.lambda.output_base64sha256, qualquer mudança no código gera um novo deploy.
Como expor a TABLE_NAME como variável?
Use o bloco environment { variables = { TABLE_NAME = var.table_name } } no resource da Lambda. No Python, acesse com os.environ["TABLE_NAME"].
Function URL retorna 403?
Confirme que authorization_type = "NONE" está definido. Se usar "AWS_IAM", as requisições precisam ser assinadas com credenciais AWS.
✅
Critério de Sucesso
# Chamar a API — deve retornar os pedidos em JSON
curl -s $(terraform output -raw function_url) | python3 -m json.tool

# Saída esperada: lista com os pedidos da tabela lab-pedidos
[
  { "cliente": "Ana Lima", "produto": "Notebook Dell", ... },
  ...
]

Lab 04 · IAM · ~35 min

IAM — Usuário, Grupo e Policy

"A ShopCloud contratou um dev júnior que só pode ler pedidos"

🎯 Contexto

Gerencie identidades AWS como código. Crie o usuário, o grupo e a policy customizada inteiramente via Terraform. Nada de clicar no console IAM. O objetivo é internalizar o conceito de least privilege: conceder apenas o que é necessário, nada mais.

📁 Estrutura esperada

lab-04-iam/ ├── main.tf # iam_user, iam_access_key, iam_group, iam_group_membership, iam_policy, group_policy_attachment ├── variables.tf # aws_region, nome_usuario, nome_grupo, table_arn ├── outputs.tf # access_key_id, secret_access_key (sensitive!) ├── provider.tf ├── versions.tf └── backend.tf

📋 Requisitos

  • R1 aws_iam_user e aws_iam_access_key para o dev júnior
  • R2 aws_iam_group e aws_iam_group_membership associando o usuário ao grupo
  • R3 aws_iam_policy com dynamodb:Scan e dynamodb:GetItem usando jsonencode(), restrito ao ARN exato da tabela
  • R4 aws_iam_group_policy_attachment associando a policy ao grupo
  • R5 Output secret_access_key marcado como sensitive = true

💡 Dicas

Como testar com o usuário criado?
Configure um segundo profile no CLI: aws configure --profile dev-junior usando as credenciais do output. Depois use --profile dev-junior nos comandos de teste.
secret_access_key some após o apply?
O Terraform mostra o secret_access_key apenas no primeiro apply. Anote imediatamente ou use terraform output -raw secret_access_key logo após o apply.
Como limitar ao ARN exato da tabela?
No campo Resource da policy use: arn:aws:dynamodb:REGION:ACCOUNT:table/lab-pedidos. Use data "aws_caller_identity" para pegar o account ID dinamicamente.
Como validar a policy antes de aplicar?
Após o apply, use aws iam simulate-principal-policy --policy-source-arn ARN-USER --action-names dynamodb:DeleteItem --resource-arns ARN-TABLE --profile SEU-PERFIL para testar sem executar a ação.
✅
Critério de Sucesso
# Com --profile dev-junior — deve FUNCIONAR
aws dynamodb scan --table-name lab-pedidos \
  --profile dev-junior --region us-east-1

# Com --profile dev-junior — deve falhar com AccessDeniedException
aws dynamodb delete-item --table-name lab-pedidos \
  --key '{"id":{"S":"teste"}}' \
  --profile dev-junior --region us-east-1

Lab 05 · CloudWatch + SNS · ~30 min

Monitoramento e Alertas

"A ShopCloud quer ser notificada quando a Lambda de pedidos falha"

🎯 Contexto

Toda a stack de monitoramento como código: tópico SNS, subscription de e-mail e alarm do CloudWatch — tudo gerenciado pelo Terraform. Um único terraform apply cria o sistema de alertas completo. Depois você força um erro na Lambda para ver o alerta em ação.

📁 Estrutura esperada

lab-05-cloudwatch-alarm/ ├── main.tf # sns_topic, sns_topic_subscription, cloudwatch_metric_alarm ├── variables.tf # aws_region, email_alerta, lambda_name, threshold ├── outputs.tf # topic_arn, alarm_name ├── provider.tf ├── versions.tf └── backend.tf

📋 Requisitos

  • R1 aws_sns_topic com nome shopcloud-alertas
  • R2 aws_sns_topic_subscription com protocol = "email" e o e-mail via variável
  • R3 aws_cloudwatch_metric_alarm monitorando metric_name = "Errors" da Lambda com namespace = "AWS/Lambda"
  • R4 alarm_actions = [aws_sns_topic.alertas.arn] disparando para o SNS
  • R5 Confirmar e-mail de subscription manualmente e forçar erro na Lambda para receber o alerta

💡 Dicas

Terraform não consegue confirmar o e-mail
A confirmação de e-mail do SNS é manual e fora do Terraform. Após o apply, acesse sua caixa de entrada e clique em "Confirm subscription". Sem isso, o estado fica PendingConfirmation e nenhum alerta é enviado.
Quais dimensions usar no alarm?
Use dimensions = { FunctionName = var.lambda_name }. Sem isso o alarm monitora todos os erros Lambda da conta, não apenas a função específica.
Como forçar erro na Lambda?
Faça upload de um arquivo JSON inválido no S3: echo "invalido" | aws s3 cp - s3://SEU-BUCKET/erro.json. O json.loads() vai lançar exceção e o CloudWatch vai registrar o erro.
Alarm demora para mudar de estado?
Com period = 60 e evaluation_periods = 1, o alarm leva até 1 minuto para processar após o erro. Aguarde 2 minutos e verifique com aws cloudwatch describe-alarms.
✅
Critério de Sucesso
# Verificar estado do alarm — deve ser ALARM após forçar erro
aws cloudwatch describe-alarms \
  --alarm-names $(terraform output -raw alarm_name) \
  --query "MetricAlarms[0].StateValue" \
  --output text --region us-east-1

# Saída esperada: ALARM

# Verificar subscription confirmada (não deve ser PendingConfirmation)
aws sns list-subscriptions-by-topic \
  --topic-arn $(terraform output -raw topic_arn) \
  --query "Subscriptions[0].SubscriptionArn" \
  --output text
