Lambda com Python

Crie sua primeira função Lambda com Terraform: IAM Role com least privilege, logs gerenciados, empacotamento automático e endpoint HTTPS sem API Gateway.

AWS Lambda Python 3.13 IAM Role CloudWatch Logs Function URL X-Ray archive_file
Contexto

A LojaFácil precisa de uma saudação inteligente

A LojaFácil precisa de uma funcionalidade simples: um serviço que recebe um nome e devolve uma saudação personalizada. Esse tipo de lógica pequena, que roda por milissegundos e só é chamada quando necessário, é o caso de uso perfeito para Lambda.

Em vez de manter um servidor ligado 24h esperando chamadas, a Lambda executa só quando é invocada — você paga apenas pelo tempo real de execução.

✅
Quando usar Lambda
Lógica pequena, eventos, webhooks, tarefas agendadas
❌
Quando não usar
Processos contínuos, tarefas acima de 15 min, estado em memória

Conceitos

Entenda antes de criar

Leia esta seção antes de rodar o terraform apply. Ela explica o porquê de cada decisão — assim você não está só copiando, está entendendo.

🪪
IAM Role — o crachá da Lambda

Quando a Lambda executa, ela precisa provar pra AWS quem ela é. A Role é esse crachá. Ela tem duas partes:

Trust Policy — define quem pode usar o crachá. Aqui: lambda.amazonaws.com. Só o serviço Lambda pode assumir essa role.

Policy Attachment — o que o crachá permite fazer. Anexamos apenas AWSLambdaBasicExecutionRole: escrever logs no CloudWatch. Nada mais.

⚠️

Nunca use AdministratorAccess em uma Lambda. Se ela for comprometida, o invasor teria poder total sobre sua conta AWS.

📦
archive_file — empacotando o código

A Lambda não aceita um arquivo .py direto — ela precisa de um .zip. O data "archive_file" faz esse empacotamento localmente:

src/hello_world.py
      ↓ (empacota local)
.build/hello_world.zip
      ↓ (upload)
AWS Lambda

É um data source, não um resource — não cria nada na AWS. Só roda localmente na sua máquina.

🔑
source_code_hash — detectando mudanças

Sem esse campo, você edita o .py, roda terraform apply e... nada acontece. O Terraform não percebe que o código mudou.

O motivo: o Terraform rastreia o estado pelos atributos. O filename do zip nunca muda — é sempre .build/hello_world.zip.

Com source_code_hash, o hash SHA256 muda quando o código muda → Terraform detecta → novo deploy. ✅

💡

Edite o .py e rode terraform plan. Procure source_code_hash no output — ele vai aparecer como changed.

🌐
Function URL — sem API Gateway

A Function URL cria um endpoint HTTPS permanente direto para a Lambda — sem precisar de API Gateway.

Function URLAPI Gateway
ConfiguraçãoSimplesComplexa
Custo extraNãoSim
RoteamentoNãoSim
🌿
Variáveis de ambiente

Valores injetados no código via Terraform — sem alterar o .py. No código você lê com os.environ.get("NOME_PADRAO").

Imagine dev e prod: comportamento diferente, código idêntico. Só as variáveis mudam.

⚠️

Nunca coloque senhas, tokens ou API keys em env vars da Lambda — ficam visíveis no console AWS. Use Secrets Manager para segredos.

⚡
depends_on — ordem de criação

O Terraform cria recursos em paralelo para ganhar velocidade. O problema: a Lambda pode ser criada antes da policy ser anexada à role.

Quando ela é invocada e tenta escrever logs — falha com erro de permissão.

IAM Role → Policy → Log Group → Lambda

Com depends_on, forçamos essa ordem e eliminamos a race condition.

O código Python que será deployado

python · src/hello_world.py
import json
import logging
import os

logger = logging.getLogger()
logger.setLevel(logging.INFO)

def lambda_handler(event, context):
    logger.info(f"Evento recebido: {json.dumps(event)}")

    # Lê o nome do evento; se não vier, usa a variável de ambiente
    nome = event.get("nome", os.environ.get("NOME_PADRAO", "Mundo"))

    resposta = {
        "mensagem": f"Olá, {nome}! Esta é minha primeira Lambda com Terraform.",
        "versao":   os.environ.get("APP_VERSION", "1.0.0"),
        "request_id": context.aws_request_id,
    }

    return {
        "statusCode": 200,
        "headers": {"Content-Type": "application/json"},
        "body": json.dumps(resposta, ensure_ascii=False),
    }
Testes

Como invocar a Lambda

Há quatro formas de testar. Experimente todas — cada uma mostra um ângulo diferente.

1 · AWS CLI
2 · curl
3 · Console AWS
4 · Logs em tempo real

A forma mais comum no dia a dia. O resultado vai para resposta.json e o cat exibe na tela.

bash
aws lambda invoke \
  --function-name $(terraform output -raw function_name) \
  --payload '{"nome":"Ana"}' \
  --cli-binary-format raw-in-base64-out \
  resposta.json && cat resposta.json

Resposta esperada:

json
{
  "statusCode": 200,
  "headers": {"Content-Type": "application/json"},
  "body": "{\"mensagem\": \"Olá, Ana! Esta é minha primeira Lambda com Terraform.\",
           \"versao\": \"1.0.0\",
           \"request_id\": \"abc-123-xyz...\"}"
}
💡

O request_id é único por invocação. Copie esse valor e procure nos logs do CloudWatch para correlacionar resposta com logs.

A Function URL permite chamadas HTTP diretas. Sem CLI, sem credenciais — só um curl.

bash
curl -s -X POST "$(terraform output -raw function_url)" \
  -H "Content-Type: application/json" \
  -d '{"nome":"Ana"}'

Você também pode abrir a URL direto no browser (GET sem body) — vai usar o NOME_PADRAO da variável de ambiente.

Hora de fazer sozinha 💪

Estes desafios foram criados para você resolver sem um passo a passo. Use o código do lab como referência e pesquise quando precisar. Isso é exatamente como funciona no trabalho real.

🥉
DESAFIO 1 · INICIANTE
Adicione a data e hora na resposta

Atualmente a Lambda retorna mensagem, versao e request_id. Sua missão é adicionar o campo timestamp com a data e hora atual da execução.

✅ Resposta esperada após o desafio:

{
  "mensagem": "Olá, Ana! Esta é minha primeira Lambda com Terraform.",
  "versao": "1.0.0",
  "request_id": "abc-123...",
  "timestamp": "2025-06-23T14:30:00.123456"
}
  • →O módulo datetime já vem com o Python (sem instalar nada)
  • →from datetime import datetime e datetime.now().isoformat() são seus amigos
  • →Depois de editar o .py, rode terraform plan — observe o source_code_hash mudar
  • →Rode terraform apply para fazer o novo deploy
🔍 Como verificar
bash
aws lambda invoke \
  --function-name $(terraform output -raw function_name) \
  --payload '{"nome":"Ana"}' \
  --cli-binary-format raw-in-base64-out \
  resposta.json && cat resposta.json
# O campo "timestamp" deve aparecer na resposta

DESAFIO 2 · INTERMEDIÁRIO
Adicione uma variável de ambiente AMBIENTE

Adicione uma nova variável de ambiente chamada AMBIENTE com valor "desenvolvimento". A resposta da Lambda deve incluir esse valor no campo ambiente.

✅ Você precisará alterar 3 arquivos:

1. variables.tf
criar variável ambiente
2. main.tf
adicionar AMBIENTE nas env vars
3. hello_world.py
ler e incluir na resposta
  • →Siga o mesmo padrão da variável NOME_PADRAO que já existe
  • →No Python: os.environ.get("AMBIENTE")
  • →Após as mudanças, o terraform plan mostrará dois changes: código Python e env vars

Invoque e confirme "ambiente": "desenvolvimento" na resposta. Depois mude o valor para "producao" no variables.tf, aplique novamente e veja a resposta mudar sem alterar uma linha de Python.

DESAFIO 3 · AVANÇADO
Valide a entrada e retorne erro 400

Atualmente, se você enviar {"nome": ""} (string vazia), a Lambda retorna "Olá, !" — um bug. Corrija para retornar statusCode 400 quando o nome for vazio.

✅ Comportamento esperado:

{"nome":"Ana"} → 200 ✅

{"statusCode": 200,
 "body": "Olá, Ana!..."}

{"nome":""} → 400 ❌

{"statusCode": 400,
 "body": "{'erro':...}"}
  • →No Python, "" é False em um if — então if not nome: funciona
  • →O statusCode faz parte do dicionário de retorno, não é uma exceção Python
  • →Não use raise Exception — Lambda retorna erros de forma controlada pelo statusCode
  • →Lembre de fazer o redeploy com terraform apply após editar o .py
🔍 Três testes para verificar
bash
# ✅ Deve retornar statusCode 200
aws lambda invoke --function-name $(terraform output -raw function_name) \
  --payload '{"nome":"Ana"}' --cli-binary-format raw-in-base64-out out.json && cat out.json

# ❌ Deve retornar statusCode 400
aws lambda invoke --function-name $(terraform output -raw function_name) \
  --payload '{"nome":""}'  --cli-binary-format raw-in-base64-out out.json && cat out.json

# ✅ Sem nome → usa NOME_PADRAO → deve retornar statusCode 200
aws lambda invoke --function-name $(terraform output -raw function_name) \
  --payload '{}'           --cli-binary-format raw-in-base64-out out.json && cat out.json
💡

Retornar statusCode 400 não é um erro da Lambda — ela executou com sucesso e devolveu uma resposta controlada. Esse é o padrão HTTP: o código indica o resultado da operação, não o estado da função.

FAQ

Dúvidas frequentes

Por que criar o log group explicitamente se a Lambda cria sozinha? ›
A Lambda cria o log group automaticamente na primeira invocação — mas sem retenção definida. Os logs ficam armazenados para sempre e geram custo crescente. Criando explicitamente no Terraform: a retenção é configurada desde o início, o terraform destroy apaga o log group junto com os outros recursos, e o estado do Terraform rastreia tudo com visibilidade total.
O que acontece se eu não colocar source_code_hash? ›
Você edita o .py, roda terraform apply e... nada acontece. O Terraform não detecta a mudança porque o caminho do arquivo (.build/hello_world.zip) não mudou. A Lambda continua rodando o código antigo silenciosamente — sem erro, sem aviso.
Por que authorization_type = "NONE" na Function URL? ›
Para simplificar o lab — a URL funciona com curl sem precisar de credenciais AWS. Em produção, use "AWS_IAM". Isso exige que o chamador tenha permissão lambda:InvokeFunctionUrl na IAM — apenas quem você autorizar consegue chamar.
A Lambda pode acessar S3, DynamoDB e outros serviços? ›
Sim — mas você precisa anexar políticas adicionais à role. Neste lab, a role só tem AWSLambdaBasicExecutionRole (logs). Se a Lambda precisar de S3, você cria uma policy específica (s3:GetObject para o bucket X) e a anexa. Sempre seguindo o least privilege — não dê s3:* se só precisa de leitura.
O que é o request_id na resposta? ›
É o identificador único de cada invocação, gerado pela AWS (context.aws_request_id). Útil para correlacionar a resposta com os logs no CloudWatch — procure esse ID nos logs para ver exatamente o que aconteceu naquela chamada. Em produção, sempre retorne o request_id nas respostas de API para facilitar debugging.

🧹 Destruindo os recursos

Ao terminar o lab, remova tudo para não gerar custo.

bash
terraform destroy

Todos os recursos são removidos: Lambda, IAM Role, Function URL e o CloudWatch Log Group (incluindo os logs armazenados).
