AWS Labs · Lab 06

Route 53: Failover com Health Check

Alta disponibilidade com DNS inteligente e detecção automática de falhas

🌐 Route 53 💻 EC2 🏗️ Terraform ❤️ Health Check 🔁 Failover DNS ☁️ us-east-1

🎯 Objetivo

Entender na prática como o Route 53 detecta falhas e redireciona o tráfego automaticamente para um servidor de backup — sem nenhuma intervenção manual.

A LojaFácil cresceu e agora precisa de alta disponibilidade. Se o servidor principal cair, o site não pode ficar fora do ar esperando alguém perceber o problema e agir. A solução é um failover automático: o Route 53 monitora o servidor principal e, ao detectar falha, passa a direcionar os clientes para o servidor de backup automaticamente.

🏗️ Arquitetura

👤 Cliente
resolve app.lojafacil-lab.com
⬡ ROUTE 53
PRIMARY
Record A · ativo
✅ health check vinculado
SECONDARY
Record A · standby
⚠️ ativa quando PRIMARY falha
❤️ Health Check · GET /health · a cada 30s
🖥️ EC2 Primária
AZ: us-east-1a
nginx + /health
🖥️ EC2 Secundária
AZ: us-east-1b
nginx + /health

Fluxo de failover

NORMAL cliente → DNS resolve PRIMARY → EC2 Primária ✅
FALHA Health check detecta 3 falhas consecutivas → ativa SECONDARY ⚠️
RECUPERAÇÃO Health check volta a passar → DNS resolve PRIMARY novamente ✅

⚠️ Diferença em relação ao Lab 05

No lab 05 usamos uma Hosted Zone privada — o DNS só resolvia dentro da VPC. Neste lab usamos uma Hosted Zone pública porque os health checks do Route 53 são executados por servidores AWS espalhados pelo mundo, fora da sua VPC.

Lab 05Lab 06
Tipo de zonaPrivadaPública
Resolução DNSSó dentro da VPCNa internet (se domínio registrado)
Health checksNão suportadoSuportado ✅
Domínio necessárioNãoPara resolver na internet (sim)
💡

Para este lab, a zona pública é criada no Route 53 mas o domínio lojafacil-lab.com não está registrado — o que importa é observar o comportamento do health check e do failover no console do Route 53.

🚀 Deploy

$ terraform init
$ terraform plan
$ terraform apply
⏳

Aguarde ~2 minutos após o apply para o nginx inicializar nas EC2 antes de começar os testes.

Anote os outputs — você vai precisar deles:

bash
terraform output ip_publico_primaria
terraform output ip_publico_secundaria
terraform output url_health_primaria
terraform output health_check_id

✅ Verificação inicial

1. Confirme que os dois servidores respondem

bash
# Deve retornar "SERVIDOR PRIMÁRIO" e código 200
curl http://$(terraform output -raw ip_publico_primaria)

# Deve retornar "SERVIDOR SECUNDÁRIO (FAILOVER)" e código 200
curl http://$(terraform output -raw ip_publico_secundaria)

2. Confirme que o endpoint de health check responde

bash
# Ambos devem retornar "OK"
curl http://$(terraform output -raw ip_publico_primaria)/health
curl http://$(terraform output -raw ip_publico_secundaria)/health

3. Observe o health check no console

🔗

Acesse console.aws.amazon.com/route53/healthchecks e aguarde o status Healthy (1-2 minutos).

🗺️

Em Route 53 → Hosted Zones → lojafacil-lab.com você verá dois registros app.lojafacil-lab.com tipo A: um PRIMARY e um SECONDARY.

🧪 Simulando o Failover

1

Derrube o nginx na EC2 primária

Conecte via SSH e pare o nginx:

bash
ssh -i lab-failover-key.pem ec2-user@$(terraform output -raw ip_publico_primaria)

# Dentro da EC2 primária:
sudo systemctl stop nginx

# Confirme — deve retornar "connection refused"
curl http://localhost/health
2

Observe o health check mudar para Unhealthy

O Route 53 tenta GET /health a cada 30 segundos. Após 3 falhas consecutivas, o status muda para Unhealthy.

⏱️

Tempo estimado para detectar a falha: 30s × 3 = ~90 segundos

Acompanhe em: console.aws.amazon.com/route53/healthchecks

3

Confirme que o failover aconteceu

Pegue um nameserver da zona e consulte o DNS diretamente:

bash · Linux/macOS/WSL/Git Bash
# Extrai o primeiro nameserver (sem dependência de python3)
NS=$(terraform output -json nameservers | tr -d '[]"' | cut -d',' -f1)
nslookup app.lojafacil-lab.com $NS
powershell · Windows
# Extrai o primeiro nameserver
$ns = (terraform output -json nameservers | ConvertFrom-Json)[0]

# Consulta usando nslookup (nativo do Windows)
nslookup app.lojafacil-lab.com $ns

# Ou com Resolve-DnsName (output mais detalhado)
Resolve-DnsName -Name app.lojafacil-lab.com -Server $ns
✅

O IP retornado deve ser o da SECUNDÁRIA. Confirme com terraform output ip_publico_secundaria.

4

Simule a recuperação

Volte para a EC2 primária e reinicie o nginx:

bash
# Dentro da EC2 primária:
sudo systemctl start nginx
curl http://localhost/health  # deve retornar "OK"

Após 2 checks consecutivos OK, o Route 53 volta a usar o registro PRIMARY.

🔍 Parâmetros do Health Check

Os valores estão em variables.tf — altere e aplique para ver o efeito:

VariávelPadrãoO que controla
health_check_intervalo30sCom que frequência o Route 53 testa o endpoint
health_check_threshold_falha3Falhas consecutivas para marcar como Unhealthy
health_check_threshold_saudavel2Sucessos consecutivos para voltar a Healthy

Experimento — acelerar o failover

hcl · variables.tf
health_check_intervalo          = 10  # mínimo permitido pelo Route 53
health_check_threshold_falha    = 2   # falha após 2 checks (20 segundos)
health_check_threshold_saudavel = 1   # recupera após 1 check (10 segundos)
💰

O intervalo de 10 segundos gera mais custo que 30 segundos — cada health check tem um preço por check realizado. Em produção, escolha o intervalo com base no SLA do serviço.

💡 Conceitos deste lab

Failover routing policy

Define um registro PRIMARY e um SECONDARY. O SECONDARY só entra em ação quando o PRIMARY está Unhealthy.

Health Check

Sonda periódica que o Route 53 envia para verificar se um endpoint está respondendo. Suporta HTTP, HTTPS e TCP.

set_identifier

Campo obrigatório quando há múltiplos registros com o mesmo nome e tipo. Diferencia os registros no Terraform e no Route 53.

health_check_id

Vincula um registro DNS a um health check. Sem isso, o Route 53 não sabe que deve remover o registro quando o servidor falhar.

TTL baixo no failover

TTL de 60s garante que clientes que cachearam o IP antigo sejam atualizados rapidamente após o failover.

AZs diferentes

As duas EC2 ficam em Availability Zones diferentes propositalmente — se uma AZ inteira cair, o backup em outra AZ continua disponível.

❓ Por que não usar zona privada aqui?

Os health checks do Route 53 são realizados por servidores AWS em múltiplas regiões do mundo. Esses servidores estão fora da sua VPC e precisam alcançar o endpoint pela internet pública. Uma zona privada só resolve nomes dentro da VPC — os health checkers não têm acesso a ela.
