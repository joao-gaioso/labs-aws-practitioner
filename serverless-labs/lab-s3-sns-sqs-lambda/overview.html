🛒
Cenário Real
Uma loja online faz upload de um arquivo pedidos.json para o S3. O sistema processa cada pedido automaticamente, sem servidores dedicados, sem gerenciar infraestrutura.
💡
Por que Serverless?
Você paga apenas pelo que usa. Zero pedidos = zero custo. A AWS escala automaticamente de 1 pedido por dia a 1 milhão — sem configuração manual de servidores.
🔗
Event-Driven
Cada serviço reage a eventos do anterior. Nenhum serviço fica em loop esperando. Isso é a essência da arquitetura orientada a eventos: baixo acoplamento, alta escalabilidade.
📏
Limite de 256 KB
SNS e SQS têm limite de 256 KB por mensagem. Por isso o S3 não envia o arquivo inteiro — envia apenas a referência (bucket + key). A Lambda busca o conteúdo diretamente no S3.
🌐 Padrão Fan-Out

O SNS pode distribuir a mesma notificação para múltiplas filas SQS simultaneamente. Isso permite que diferentes microsserviços (estoque, financeiro, logística) processem o mesmo pedido de forma independente e paralela.

⚠️ Atenção: float vs Decimal no DynamoDB

O boto3 (SDK Python da AWS) rejeita valores float ao salvar no DynamoDB. Use sempre Decimal('9.99') em vez de 9.99 para evitar o erro Float types are not supported. Isso protege a precisão de valores monetários.

🔧 Os Serviços do Lab

🪣
Amazon S3
Simple Storage Service — Armazenamento de objetos
O S3 é o ponto de entrada do lab. Quando o arquivo pedidos.json é carregado, o S3 dispara uma notificação de evento para o SNS. Ele não processa nada — apenas armazena e avisa. No lab, a Lambda lê o arquivo diretamente do S3 usando o boto3, pois o conteúdo do arquivo ultrapassa o limite de mensagem do SNS/SQS.
📣
Amazon SNS
Simple Notification Service — Pub/Sub
O SNS funciona como um megafone: publica a notificação de upload para todos os subscribers cadastrados. No lab, ele tem uma fila SQS como subscriber. Em produção real, poderia ter e-mail, SMS, HTTP endpoint e múltiplas filas SQS ao mesmo tempo (fan-out). Limite: 256 KB por mensagem.
📬
Amazon SQS
Simple Queue Service — Fila de mensagens
A fila SQS é o buffer entre o SNS e a Lambda. Ela garante que a mensagem não seja perdida se a Lambda falhar. O Visibility Timeout esconde a mensagem enquanto a Lambda processa; se a Lambda falhar antes de deletar, a mensagem fica visível novamente para reprocessamento automático.
⚡
AWS Lambda
Compute serverless — Execução sob demanda
A Lambda é o cérebro do processamento. Ela: (1) recebe o evento da SQS, (2) extrai o bucket/key do arquivo, (3) baixa o JSON do S3, (4) itera sobre cada pedido, (5) salva no DynamoDB. Roda em Python 3.12, sem servidor para gerenciar. O Cold Start pode adicionar latência na primeira execução após inatividade.
🗄️
Amazon DynamoDB
NoSQL totalmente gerenciado — Chave-valor e documentos
O DynamoDB é o destino final dos pedidos processados. No lab, a tabela lab-pedidos usa pedido_id como partition key. É serverless, escala automaticamente e cobra por leitura/escrita. Cuidado com tipos: usa Decimal para números decimais, nunca float.

Quando usar qual padrão?

Padrão Quando usar Exemplo
SQS → Lambda Um único consumidor, sem fanout necessário Processamento simples de formulários
SNS → Lambda Notificação síncrona sem buffer Alertas de monitoramento
S3 → SNS → SQS → Lambda Arquivo grande + múltiplos consumidores + resiliência Processamento de pedidos (este lab!)
S3 → Lambda Trigger direto, arquivo pequeno, sem fanout Redimensionar imagens no upload
SNS → SQS (múltiplas) Fan-out para microsserviços independentes Estoque + Financeiro + Logística
⏱️
Visibility Timeout
Enquanto a Lambda processa, a mensagem fica "invisível" na fila. Se a Lambda confirmar (delete), a mensagem some. Se falhar, ela volta para a fila automaticamente após o timeout — garantindo reprocessamento sem perda de dados.
❄️
Cold Start Lambda
A primeira invocação após um período de inatividade demora mais porque a AWS precisa provisionar o container. Em produção, use Provisioned Concurrency para workloads sensíveis à latência.
🔐
IAM — Permissões Mínimas
A role da Lambda deve ter apenas o necessário: s3:GetObject no bucket específico, dynamodb:PutItem na tabela específica, e sqs:ReceiveMessage + sqs:DeleteMessage na fila.

🚀 Passo a Passo do Lab

📋 Pré-requisito

Você precisa ter a AWS CLI configurada (aws configure), permissões para criar recursos S3/SNS/SQS/Lambda/DynamoDB, e o PowerShell ou terminal bash disponível.

1

Empacotar o código Lambda

Crie o arquivo zip com o código Python da função Lambda. Execute no PowerShell dentro da pasta do lab:

Compress-Archive -Path lambda_function.py -DestinationPath lambda.zip -Force
2

Executar o script de deploy

O script deploy.sh cria todos os recursos AWS automaticamente: bucket S3, tópico SNS, fila SQS, role IAM, função Lambda e a tabela DynamoDB.

./deploy.sh
3

Fazer upload do arquivo de pedidos

Copie o arquivo pedidos.json para o bucket S3. Esse upload é o gatilho que inicia todo o fluxo de eventos. Substitua SEU-BUCKET pelo nome gerado no deploy:

aws s3 cp pedidos.json s3://SEU-BUCKET/pedidos.json
4

Verificar os pedidos no DynamoDB

Aguarde cerca de 10 segundos e consulte a tabela para confirmar que os pedidos foram gravados com sucesso:

aws dynamodb scan --table-name lab-pedidos
5

Acompanhar os logs da Lambda em tempo real

Para monitorar o processamento ao vivo, use o CloudWatch Logs. O --follow mantém o terminal aberto aguardando novos logs:

aws logs tail /aws/lambda/lambda-processa-pedidos --follow
6

Limpar todos os recursos

Ao terminar o lab, execute o script de limpeza para deletar todos os recursos criados e evitar cobranças desnecessárias na sua conta AWS:

./cleanup.sh

🔍 O que acontece nos bastidores?

# 1. Você faz upload do arquivo
aws s3 cp pedidos.json s3://meu-bucket/pedidos.json

# 2. S3 detecta o evento PutObject e publica no SNS
SNS.publish(
  TopicArn="arn:aws:sns:us-east-1:123:lab-topic",
  Message="{bucket: 'meu-bucket', key: 'pedidos.json'}"
)

# 3. SNS entrega a mensagem para a fila SQS
SQS ← mensagem com referência ao arquivo S3

# 4. Lambda é acionada pela SQS (event source mapping)
def lambda_handler(event, context):
  body = json.loads(event['Records'][0]['body'])

# 5. Lambda baixa o arquivo diretamente do S3
  obj = s3.get_object(Bucket=bucket, Key=key)
  pedidos = json.loads(obj['Body'].read())

# 6. Lambda processa cada pedido (float → Decimal!)
  for pedido in pedidos:
    pedido['preco'] = Decimal(str(pedido['preco']))

# 7. Lambda salva cada pedido no DynamoDB
    table.put_item(Item=pedido)

# 8. Lambda confirma e a mensagem é deletada da SQS
SQS.delete_message(ReceiptHandle=...)

🏆 Desafios para Praticar

1️⃣ INICIANTE Adicionar um novo campo ao pedido
Edite o arquivo pedidos.json e adicione um novo campo em todos os pedidos, por exemplo "categoria": "eletronicos". Faça o upload novamente e verifique se o novo campo aparece nos itens do DynamoDB após o processamento.

O que você aprende: O DynamoDB é schemaless — você pode adicionar campos livremente sem alterar a estrutura da tabela.
💡 Dica: Use aws dynamodb scan --table-name lab-pedidos --output table para visualizar os dados de forma mais legível no terminal.
2️⃣ INTERMEDIÁRIO Processar múltiplos arquivos
Crie um segundo arquivo chamado pedidos2.json com 3 pedidos diferentes (use IDs únicos como P004, P005, P006). Faça o upload para o mesmo bucket e verifique se todos os pedidos de ambos os arquivos aparecem no DynamoDB.

O que você aprende: Cada upload é um evento independente. O fluxo S3→SNS→SQS→Lambda processa cada arquivo separadamente de forma assíncrona.
💡 Dica: Execute aws dynamodb scan --table-name lab-pedidos --select COUNT para contar o total de itens na tabela rapidamente.
3️⃣ AVANÇADO Adicionar uma Dead Letter Queue (DLQ)
Configure uma Dead Letter Queue na fila SQS principal para capturar mensagens que falharem após 3 tentativas de processamento. Crie uma segunda fila SQS chamada lab-pedidos-dlq e configure a fila principal para redirecionar mensagens problemáticas para ela automaticamente.

O que você aprende: A DLQ é um pattern essencial de resiliência. Em vez de perder mensagens que causam erros, você as isola para análise e reprocessamento manual.

📋 Passo a passo para configurar:

1. Criar a fila DLQ:
aws sqs create-queue --queue-name lab-pedidos-dlq --region us-east-1
2. Configurar o RedrivePolicy na fila principal:
Este é o passo essencial — sem ele a DLQ existe mas nunca recebe nada. O RedrivePolicy diz ao SQS: "após maxReceiveCount tentativas fracassadas, mova a mensagem para esta DLQ". Execute o comando abaixo com seu Account ID:
aws sqs set-queue-attributes \
  --queue-url "https://sqs.us-east-1.amazonaws.com/SEU-ACCOUNT-ID/lab-pedidos-queue" \
  --attributes "{\"RedrivePolicy\":\"{\\\"deadLetterTargetArn\\\":\\\"arn:aws:sqs:us-east-1:SEU-ACCOUNT-ID:lab-pedidos-dlq\\\",\\\"maxReceiveCount\\\":\\\"2\\\"}\"}" \
  --region us-east-1
3. Confirmar que o RedrivePolicy foi aplicado:
Se o comando anterior não retornar erro, confirme que o redrive foi gravado corretamente — a fila precisa mostrar o atributo RedrivePolicy na saída:
aws sqs get-queue-attributes \
  --queue-url "https://sqs.us-east-1.amazonaws.com/SEU-ACCOUNT-ID/lab-pedidos-queue" \
  --attribute-names RedrivePolicy \
  --region us-east-1
Se RedrivePolicy aparecer no output com o ARN da DLQ e o maxReceiveCount, a configuração está correta. Se o output vier vazio, o passo 2 não foi aplicado — repita-o.

⚠️ Atenção: Se a fila principal não tiver o RedrivePolicy configurado, a mensagem ficará sendo recebida e devolvida à fila indefinidamente, nunca irá para a DLQ, independentemente de quantas vezes falhar.

🔥 Como provocar uma falha para testar a DLQ:
A DLQ só recebe mensagens quando a Lambda lança uma exceção não tratada. No código atual, erros são capturados internamente e a mensagem é deletada mesmo com falha. Você precisa forçar uma falha real. Existem duas formas:

Opção A — Arquivo JSON inválido (mais fácil):
Crie um arquivo com JSON malformado para que o json.loads() da Lambda quebre com exceção não capturada:
echo "isso nao e um json valido!!!" > pedidos-invalido.json aws s3 cp pedidos-invalido.json s3://SEU-BUCKET/pedidos-invalido.json
Opção B — Apagar a tabela DynamoDB (força erro no put_item):
Apague a tabela lab-pedidos no console enquanto a Lambda está rodando. Ela vai falhar ao tentar gravar — e a mensagem vai ser recolocada na fila pelo SQS automaticamente.

⚙️ Para ver a mensagem "morrer" e ir para a DLQ:
Com maxReceiveCount=3, a Lambda precisa falhar 3 vezes na mesma mensagem. O SQS só redireciona para a DLQ após a 3ª falha. Para acelerar o teste, antes de enviar o arquivo inválido, desative o trigger Lambda e envie a mensagem manualmente para a fila — assim você controla quantas vezes a mensagem é recebida:
# 1. Verificar mensagens na DLQ (deve aparecer após as 3 falhas)
aws sqs get-queue-attributes \
  --queue-url https://sqs.us-east-1.amazonaws.com/SEU-ACCOUNT-ID/lab-pedidos-dlq \
  --attribute-names ApproximateNumberOfMessages \
  --region us-east-1

# 2. Ler o conteúdo da mensagem que foi para a DLQ
aws sqs receive-message \
  --queue-url https://sqs.us-east-1.amazonaws.com/SEU-ACCOUNT-ID/lab-pedidos-dlq \
  --region us-east-1
O que você verá na DLQ: a mensagem original intacta — o evento S3/SNS completo que causou a falha, incluindo o nome do arquivo problemático. Em produção, uma equipe de suporte usaria essa mensagem para investigar a causa raiz e reprocessar manualmente após corrigir o problema.
4️⃣ EXPERT Notificação por e-mail via SNS
Adicione um segundo subscriber no tópico SNS que envia um e-mail sempre que um novo arquivo de pedidos chega. Enquanto a fila SQS continua alimentando a Lambda (processamento automático), o e-mail serve como notificação para a equipe de operações.

O que você aprende: Este é o padrão fan-out em ação: um único publisher (SNS) notificando múltiplos subscribers simultaneamente, cada um fazendo algo diferente com o mesmo evento.
💡 Dica: No console AWS, vá em SNS → seu tópico → Create subscription → Protocol: Email → insira seu e-mail. Confirme o e-mail de verificação que a AWS enviará antes de testar.
